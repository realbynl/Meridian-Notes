# UI toolkit milestone 2: ribbon, menus, dialogs: design

> **DRAFT: not approved. Written while the user was away (2026-10-13). Nothing here is implemented. The Open Questions need the user's answers before a plan is written.**

Milestone 2 of `docs/superpowers/specs/2026-10-13-ui-toolkit-design.md`: "Ribbon, menus, dropdowns, dialogs, tooltips, text inputs, keyboard focus." Milestone 1 (three-pane chrome) is built (`docs/ui-toolkit.md`).

## What already exists (read in the code, 2026-10-13)

**Toolkit (`crates/ui`, milestone 1).** Headless crate: `layout.rs` (`Node` tree, `Id { kind, index }`, row/column flex with `Fixed`/`Fill`/`Content`), `canvas.rs` (clip, fill, stroke, alpha blit), `fills.rs` (solid, gradient, picture paints; scaled-picture cache), `slice.rs` (nine-slice), `text.rs` (`TextEngine`, faces `Ui`/`UiBold`/`Mono`, width and glyph caches, `fit` with ellipsis), `style.rs` (`StyleSheet::from_skin`, a `Look` per widget `W` and `State`, size `Slot`s, icons), `chrome/build.rs`, `chrome/paint.rs`, `chrome/pointer.rs` (hover, press, capture, drags, wheel, double-click, per-widget damage). `crates/gui/src/shell.rs` (`Shell`) joins it to the app each frame. Rules already in force: no layout work on typing frames, damage per widget, partial paint equals full paint (tested), lists virtualised.

**Skin keys.** `skin_ui.rs`: `WIDGETS` (`window notebooks sections pages title status splitter scrolltrack scrollthumb button sectiontab listrow`), `STATES` (`normal hover pressed active selected disabled`), `PROPS` (`bg fg border font size`), `SLOTS` (11, with `SLOT_DEFAULTS`), `ICON_NAMES` (7, Nerd Font `ICON_DEFAULTS`). Grammar `ui.<widget>.<state>.<prop>`; docs table regenerated by `UPDATE_SKINS_DOC=1 cargo test -p meridian-app skins_ui_doc`. Inter is bundled for widget text (`crates/gui/assets/UI-*.ttf`).

**App boundary.** `chrome_model.rs`: `ChromeModel` (plain data, versioned), `UiAction` (`SelectNotebook/Section/Page`, `NewPage`, `NewSection`, `ResizePane`, `ToggleSidebar`, the last **reserved for this milestone**: handled by the app, sent by no widget yet). `App::handle_action` in `app/uihost.rs`. Keys always go to the app in milestone 1.

**Commands.** `commands.rs`: about 270 `e!(name, key, Cmd)` entries; `Entry { name, key, icon, make }`; `builtin_icon(name)` gives a Nerd Font glyph; `Keymap` has `bound()`, `default_key()`, `name()`, `icon()`, and applies `keys.conf`. Plugins register commands too (`Cmd::Plugin`). This registry is the single source for buttons, menu items and their shortcut labels.

**Menus today (cell-drawn).** `menu.rs`: `MENUS`, a static table `File, Edit, Selection, Find, View, Goto, Tools, Project, Preferences, Help`, each item `Cmd(command-name, label)` or `Sep`; `Bar` keyboard navigation; `AltTap` (a lone Alt tap opens the bar; Alt press/release reaches the GUI, `docs/gui-parity.md`). Context menu: `app/ctxmenu.rs` (`Ctx { rows: Vec<(&str, Cmd)>, sel, at, rect }`, right-click or `Menu`/`Shift+F10`, `draw_ctx`, `ctx_mouse`). Ctrl+K insert menu: `app/insertmenu.rs` (`Item` enum with icons and mnemonic letters). Other cell overlays drawn by the app into the grid: quick settings (`app/quickui.rs`), the full settings panel (`settings_q` in `app.rs`), key bindings (`app/keysui.rs`), dropdowns (`draw_dropdown`), new-file menu (`draw_new_menu`), goto, find bar (`findbar.rs`), command palette, mode picker, colour picker, layouts, cards, quiz and more (`draw_*` in `app/*.rs`).

**The gap** (`docs/gui-parity.md`): in the hosted chrome (the default) there is no menu bar, no menu button and no document tabs, so menus and switching or closing documents are keyboard-only. `MERIDIAN_CELL_CHROME=1` brings back the cell chrome with mouse menus. Ruled acceptable for milestone 1; this milestone closes it.

**Not in the tree:** `accesskit` (not in `Cargo.lock`), any native menu crate. Both would need the user's approval.

## Goals
1. Mouse access to every command group: a ribbon (tabs, groups, icon buttons, dropdowns), a File/backstage menu, context menus as widgets.
2. Open-document tabs as widgets (closes the gap).
3. Dialog, tooltip and single-line text-input widgets, with keyboard focus and Tab navigation.
4. Everything skinnable through `ui.*` keys; game-style skins still possible (D18).
5. Latency budgets unchanged; typing frames still paint no chrome.

Non-goals: the D10 pixel editor (milestone 3), a customisable ribbon editor (later; a config file is enough), rich text formatting commands that need the pixel engine (bold button inserts `**` for now).

## Layout (a notebook app as the target)
```
+--------------------------------------------------------------+
| File | Home | Insert | View | ...                [search] [^] |  <- ribbon tab row (collapsible)
| [Paste|v] [Cut][Copy] | [B][I][S] [Bullets] | [Task][Tag|v] |  <- active tab: groups of buttons
|   Clipboard           |   Text              |   Tags         |  <- group captions
+-----------+----------------------------------+---------------+
| Notebooks | [Section] [Section] ...          |               |
|           | [doc tab][doc tab x]             | Pages         |  <- open documents strip (new)
|           |  Page title / editor grid        |               |
+-----------+----------------------------------+---------------+
| status bar                                                   |
```
- The ribbon collapses to the tab row (double-click a tab, or `[^]`, or Ctrl+F1 as in Office); collapsed state in `settings.conf` (`ui.ribbon.collapsed`, additive).
- Small windows: groups shrink large buttons to small ones, then to a group dropdown (Office's adaptive ribbon), deterministic order, golden-tested.

## Ribbon content model
Data, not code: a static default table like `menu.rs`, overridable by a user file `<config>/ribbon.conf` (Open Question 4).
```
tab Home
  group Clipboard: paste(large) cut copy
  group Text: bold italic strike | heading-menu
  group Tags: toggle-task tag-menu
tab Insert
  group Insert: insert-menu link embed date table picture
tab View
  group Show: toggle-sidebar toggle-minimap toggle-line-numbers toggle-backlinks
  group Window: split-columns split-rows fullscreen toggle-interface skin-use
```
- Each button is a **command name**; label from a ribbon label table (fallback: the menu label in `menu.rs`, then the command name), icon from `ui.icon.cmd.<name>` (skin) else `builtin_icon(name)` else a generic glyph, tooltip "Label (Ctrl+S)" with the key from `Keymap` (so user rebinding in `keys.conf` shows up automatically).
- Plugin commands can be placed by name; a missing command hides its button (no crash).
- Disabled state: a new cheap query `App::cmd_enabled(name) -> bool` (e.g. paste with empty clipboard stays enabled; "follow link" disabled off a link). Computed only when the model version changes, never per typing frame.
- Toggles (sidebar, minimap) show `active` state from a `ChromeModel` field set.
- Dropdown buttons (`|v`) open a menu widget listing commands.

## New widgets
| widget | notes |
|---|---|
| `RibbonTabs`, `RibbonGroup`, `RibbonButton` (large/small/icon-only), `SplitButton` | build from the table; adaptive shrink |
| `MenuPopup` | layered popup above everything; submenus; keyboard (arrows, Enter, Esc, mnemonics); separators from `Item::Sep`; shortcut labels right-aligned |
| `DocTabs` | open documents, dirty dot, close button, middle-click close, overflow chevrons (reuse `SectionTabStrip` code) |
| `Tooltip` | delayed (500 ms), one at a time, a timer wake (no idle CPU while waiting: use `App::next_wake`-style deadline) |
| `TextInput` | single line: caret, selection, IME commit, clipboard via existing helpers; used by search box, dialogs, editable page title |
| `Dialog` | modal box, title, body rows, buttons; focus trap; Esc cancels |
| `Checkbox`, `Dropdown` (select) | for settings dialogs |

`UiAction` grows: `RunCommand(String)` (any registry command by name), `SelectDoc(u64)`, `CloseDoc(u64)`, `MenuOpen(MenuId)`, `TextChanged(WidgetId, String)`, `DialogResult(..)`. `RunCommand` is the key addition: the cell menu bar already returns a command name (`menu::Bar::pick`) that the app runs, so every button reuses existing behaviour.

## Keyboard focus and navigation
- Focus owner: the editor (default) or a toolkit widget. Keys go to the toolkit only while a widget has focus (menu open, dialog, text input, KeyTips mode); otherwise to the app exactly as now.
- Alt tap (`AltTap` already detects it) shows **KeyTips** (Office's letter badges) on ribbon tabs and then buttons; Esc steps back. In the cell chrome Alt tap still opens the old menu bar.
- F6 cycles regions (ribbon, notebooks, sections, editor, pages, status); Tab/Shift+Tab move inside a dialog or ribbon group; arrows inside lists and menus.
- Focus ring drawn with `ui.focus.*` keys.

## Accessibility
Real screen-reader support needs `accesskit` (+ `accesskit_winit`): a new dependency, so it needs your approval (roadmap Wave 5 says the same). The tree built each frame maps well onto it (stable ids, roles, labels from the command table). Without it: full keyboard access, KeyTips, focus rings, contrast guard on widget text (exists for skins). Recommendation: design ids/roles/labels now so accesskit can be added in a later task, and ask then.

## Existing cell overlays: migrate or coexist
They keep working: they draw inside the hosted grid rectangle and take keys as today. Migration order by value:
1. **Menu bar** (`menu.rs`): replaced in the GUI by the ribbon plus a File menu built from the same `MENUS` table (a `MenuPopup` per title, reachable from a "More" button). The cell bar stays for the terminal and `MERIDIAN_CELL_CHROME=1`.
2. **Context menu** (`ctxmenu.rs`): the row list becomes a `MenuPopup` in the GUI, same `rows` data.
3. **Ctrl+K insert menu**: becomes the Insert tab plus a popup; data from `insertmenu.rs` `Item`.
4. **Quick settings / settings panel / key bindings**: later, as dialogs, once `TextInput`, `Checkbox`, `Dropdown` exist; until then they stay cell overlays.
5. Palette, find bar, goto, pickers: stay cells until milestone 3 (they live in the editor area anyway).

Rule: one source of data per menu, two renderers (cells for the terminal, widgets for the GUI). No behaviour forks.

## Skin keys (additions, all optional)
- Widgets added to `WIDGETS`: `ribbon`, `ribbontab`, `ribbongroup`, `ribbonbutton`, `menu`, `menuitem`, `doctab`, `tooltip`, `input`, `dialog`, `checkbox`, `focus`, `keytip`. States reuse `STATES`; a `focus` state may be needed (Open Question 6).
- Slots: `ui.ribbon.height`, `ui.ribbontab.height`, `ui.ribbonbutton.large`, `ui.ribbonbutton.small`, `ui.menuitem.height`, `ui.doctab.height`, `ui.tooltip.delay` (ms; a behaviour-ish slot: check it fits the "skins style, never change behaviour" rule), `ui.dialog.padding`.
- Icons: `ui.icon.cmd.<command-name>` for any command, plus `menu-arrow`, `close`, `collapse`, `check`.
- Defaults derive from the palette like milestone 1; `examples/skins/violet/` gains a ribbon look.

## Icon art
Defaults are Nerd Font glyphs from the bundled JetBrains Mono Nerd Font (already used by `builtin_icon` and `ICON_DEFAULTS`): zero size cost, monochrome, recolourable by `fg`. a notebook app's coloured 32 px icons cannot be copied (our own art only, as the milestone 1 spec says). Options: (a) glyphs only; (b) a small own-drawn coloured PNG set in an example skin folder (not the binary); (c) commission art. Recommendation: (a) now, (b) as an example skin.

## Latency
- Ribbon is static between model changes: built once, repainted only on hover/press damage. Typing frames: no ribbon work (extend `typing_frames_paint_no_chrome` to cover ribbon and doc tabs).
- `cmd_enabled` evaluated on model-version change only, for the visible buttons only (tens).
- Popups paint over the grid: damage the popup rect on open, restore by repainting the grid region under it on close (the grid buffer is kept; copy back, no app redraw).
- Tooltip and KeyTip timers use deadlines, not polling (idle 0%).
- Startup: ribbon table is static data; the first paint gains roughly a few dozen glyph draws; re-measure the 60 ms budget (currently 29-40 ms, `docs/perf.md`).

## Test plan (outline)
- Layout goldens: ribbon at 1x/1.5x/2x, adaptive shrink at several widths, collapsed ribbon, doc-tab overflow.
- Command mapping: every command named in the default ribbon table exists in `commands::builtin()` (test fails on a typo); tooltip shows the rebound key after a `keys.conf` change.
- Pointer: button press emits `RunCommand`; dropdown opens a menu; click outside closes; capture rules as milestone 1.
- Keyboard: Alt tap KeyTips, F6 cycle, menu arrows/mnemonics/Esc, dialog focus trap, text input editing and IME commit.
- Paint: partial equals full, popup open/close restores the grid exactly, tooltip damage only its rect.
- Terminal regression: the cell menu bar and ctx menu unchanged (golden).
- Perf: typing frames with the ribbon shown paint no chrome; startup re-measured.

## Approaches
1. **Thin (A).** Doc tabs, a single "Menu" button opening `MENUS` as widget popups, widget context menu. No ribbon. ~5 tasks. Closes the parity gap fast.
2. **Recommended (B).** A first (as phase 1), then the ribbon (Home/Insert/View) from a data table, tooltips, KeyTips, then text input and dialogs, then settings as dialogs. ~13 tasks over 3-4 sessions; each phase usable alone.
3. **Native OS menus (C).** A native menu bar crate (e.g. `muda`) for File/Edit menus. Rejected unless you want it: new dependency, does not skin, inconsistent on Wayland/Hyprland.

## Risks
- **Two renderers per menu drift apart.** Mitigation: one data table, tests that both renderers list the same commands.
- **Focus bugs steal editor keys** (the worst failure for a text editor). Mitigation: the editor owns focus unless a popup/dialog/input is open; tests for every open/close path; Esc always returns focus.
- **Popup over grid leaves stale pixels.** Mitigation: grid buffer restore plus the existing partial-equals-full test style.
- **Ribbon height eats editor rows** on small screens. Mitigation: collapse, adaptive shrink, auto-collapse under a height threshold.
- **`TextInput` scope** (IME preedit is not shown even in the editor today, `docs/gui-parity.md`). Mitigation: commit-only IME in v1, same as the editor.
- **Look fidelity**: our own art will look "notebook-like", not identical; set expectations.
